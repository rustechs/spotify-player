#### B2. Tracks without a Spotify id panic the player-event watcher and the event thread — FORK (trigger) / UPSTREAM (panic sites)
- Where: [`desktop_spotify.rs:993`](../../spotify_player/src/desktop_spotify.rs:993) (`spotify_track_id_from_mpris_text` returns `None` for anything but a 22-char track id), [`desktop_spotify.rs:809`](../../spotify_player/src/desktop_spotify.rs:809) (`FullTrack { id: track_id, .. }`), [`client/mod.rs:2300`](../../spotify_player/src/client/mod.rs:2300) (`overlay_desktop_mpris` stores it in `player.playback`); panic sites [`client/handlers.rs:139`](../../spotify_player/src/client/handlers.rs:139) and [`:166`](../../spotify_player/src/client/handlers.rs:166) (`track.id.clone().expect("null track_id")`), [`event/mod.rs:884`](../../spotify_player/src/event/mod.rs:884) (`expect("all non-local tracks have ids")` on `g c`).
- Failure scenario: `[desktop_spotify] enable = true`, Connect has no session, desktop Spotify plays a local file (`mpris:trackid` = `/com/spotify/local/…`), an ad, or a podcast episode. `handle_playback_change_event` runs on the `player-event-watcher` std thread ([`main.rs:178`](../../spotify_player/src/main.rs:178)), hits the `expect`, and the panic hook at [`main.rs:73-79`](../../spotify_player/src/main.rs:73) writes it only to the `.backtrace` file, so the thread dies with nothing in the TUI or log. From then on: no track-end refresh, no context/lyrics refresh, no Connect-mode 5 s poll. The same item plus `g c` unwinds the event thread: keyboard dead while the UI keeps drawing. Connect itself can also return local tracks with `id: null`, so the upstream sites are reachable without the fork. The README advertises "desktop Spotify playing local/lossless files" as a use case.
- Fix (primary): replace the three `expect`s with early returns so an id-less item is simply skipped for track-end/queue/jump logic; the MPRIS overlay must keep showing local files, which the README advertises. Secondary: extend the panic hook to also `tracing::error!` so the Logs page shows it, and wrap the named watcher threads in a restart loop. Do not "fix" this by dropping the overlay when no id parses.

#### B3. `system_audio` capture loop spawns `pactl get-default-sink` on every ~10 ms read — FORK
- Where: [`system_audio.rs:80`](../../spotify_player/src/system_audio.rs:80) (`resolve_source(source_cfg)` on every loop iteration), [`:184`](../../spotify_player/src/system_audio.rs:184) (`Command::new("pactl")`).
- Failure scenario: with `system_audio_source = "auto"` (default) the thread fork/execs `pactl` and does a PipeWire connect/disconnect once per 480-frame read, on the order of 100 times per second, for as long as the local sink is inactive (including when nothing is playing at all). On classic PulseAudio or a loaded system where `pactl` exceeds the 10 ms read period the server-side capture buffer grows and the visualizer lags audible playback by seconds.
- Fix: resolve the source only when (re)opening the stream; re-check on read failure or a coarse timer (2–5 s). Longer term, open `@DEFAULT_MONITOR@` or subscribe to default-sink changes via `libpulse_binding` and drop the `pactl` dependency.

#### B4. Blocking process spawns and `thread::sleep` inside async code on tokio workers — FORK
- Where: `ensure_awake` ([`desktop_spotify.rs:113`](../../spotify_player/src/desktop_spotify.rs:113)) and everything it calls: `wait_for_mpris` ([`:227`](../../spotify_player/src/desktop_spotify.rs:227), `dbus-send` per 400 ms poll), `nudge` ([`:512`](../../spotify_player/src/desktop_spotify.rs:512)) → `pause_until_silent` ([`:1040`](../../spotify_player/src/desktop_spotify.rs:1040), `thread::sleep(100 ms)` loop up to 2 s), `hide_window` ([`:267`](../../spotify_player/src/desktop_spotify.rs:267), `xdotool` per 200 ms), `keep_hiding` ([`:327`](../../spotify_player/src/desktop_spotify.rs:327), `xdotool search` plus one `getwindowname` per window every 100 ms for 45 s), `PulseMuteGuard::drop` ([`:1234`](../../spotify_player/src/desktop_spotify.rs:1234), joins a thread that polls `pactl` every 40 ms). `overlay_desktop_mpris` ([`client/mod.rs:2735`](../../spotify_player/src/client/mod.rs:2735)) runs inside `retrieve_current_playback` and spawns up to seven `dbus-send` processes per call ([`desktop_spotify.rs:702`](../../spotify_player/src/desktop_spotify.rs:702)), i.e. every 5 s in Connect mode plus each `update_playback` burst.
- Failure scenario: each call pins a runtime worker for hundreds of milliseconds to tens of seconds. The `Player(_)` arm of `start_client_handler` ([`client/handlers.rs:61`](../../spotify_player/src/client/handlers.rs:61)) awaits the request inline, so while `Resume` is inside `wait_for_mpris` (default `ready_timeout_secs = 45`, longer than `CLIENT_REQUEST_TIMEOUT = 30`) every other request (playback poll, search, context fetch, CLI socket commands) queues behind it. `tokio::time::timeout` cannot cancel a future that is inside a blocking syscall; the 30 s cap is honoured only at the next `.await`.
- Fix: (1) run every `Command::new`/`thread::sleep` site behind `tokio::task::spawn_blocking` or on a dedicated wake thread that reports back over a channel; (2) replace `dbus-send` with the `dbus` crate, already linked transitively via `souvlaki` on Linux (`cargo tree -i dbus`), so MPRIS reads are one in-process `GetAll`; (3) cache the MPRIS snapshot for ~1 s so the playback poll and `update_playback` bursts do not re-query.

#### B5. Live bearer token logged verbatim at INFO on every refresh — UPSTREAM (security)

- Failure scenario: ratatui's `Block` writes only borders/title and `Paragraph` writes only the graphemes it renders; every interior cell the message does not cover keeps the page's glyphs, recoloured in the toast style. On the Liked Tracks page a "Copied link" card shows the rest of the table row inside the box; a 6-row error card shows four rows of table text. #### B7. Capture thread's yield path clears `local_sink_active`, so both audio sources then write the same band buffer — FORK
- Where: [`system_audio.rs:65-71`](../../spotify_player/src/system_audio.rs:65) (`if bands.lock().local_sink_active { if was_capturing { … processor.reset(); …`), [`vis.rs:232-243`](../../spotify_player/src/vis.rs:232) (`reset()` sets `is_active = false; local_sink_active = false; clear_intro()`), [`streaming.rs:277-281`](../../spotify_player/src/streaming.rs:277) (only `PlayerEvent::Playing` sets the flag back).
- Failure scenario: `enable_system_audio_visualization = true` with integrated streaming. App starts idle → capture thread reads once (`was_capturing = true`) → user plays locally → `Playing` sets the flag → capture thread sees it, calls `reset()` which clears the flag it just yielded to, sleeps 100 ms, reopens the monitor and resumes pushing. For the rest of the track the librespot sink (44.1 kHz) and the Pulse monitor (48 kHz, delayed) both call `run_hop`; `VisBands::sample_rate` flips per hop so the Hz tick positions jitter every frame and bars smear between two time-offset sources. Repeats on every pause/resume.
- Fix: give `BandProcessor` a buffer-only reset (clear `sample_buf`, set `warm_start`, zero `values`) that does not touch `local_sink_active` or the intro; keep `reset()` for `VisualizationSink::stop` only.

### 2.2 Should-fix

#### Desktop wake (Linux)
- **S1. Two concurrent 45 s `keep_hiding` loops after an early launch; the first is never aborted** — FORK. [`desktop_spotify.rs:93`](../../spotify_player/src/desktop_spotify.rs:93) spawns and drops the handle; [`:126`](../../spotify_player/src/desktop_spotify.rs:126) `launched_early = EARLY_LAUNCH.swap(false)`; [`:139`](../../spotify_player/src/desktop_spotify.rs:139) spawns a second loop because `launched = launched_early || needs_launch`; [`:162`](../../spotify_player/src/desktop_spotify.rs:162) aborts only the second, and not at all on the early `?` return at [`:159`](../../spotify_player/src/desktop_spotify.rs:159). Scenario: user opens the Spotify window from the tray within 45 s of TUI start and it is re-minimized every 100 ms. Fix: keep one cancellable watcher owned by the module and abort it from `ensure_awake`.
- **S2. Spotify's `prefs` file is rewritten non-atomically, sometimes while Spotify is running** — FORK. [`desktop_spotify.rs:478-509`](../../spotify_player/src/desktop_spotify.rs:478) (`set_prefs_bool` read/modify/`fs::write`), called from [`:136`](../../spotify_player/src/desktop_spotify.rs:136) when `launched_early` is true. Scenario: Spotify rewrites `prefs` on exit; a concurrent partial write truncates it or our change is lost. Editing another app's config is also a surprising side effect of `start_minimized`. Fix: write only before launch, temp file + `rename`, and document the pref edit in `docs/config.md`.
- **S3. Error classification by substring on the whole error chain** — FORK. [`client/mod.rs:2678-2699`](../../spotify_player/src/client/mod.rs:2678) (`is_rate_limit_msg` matches `"429"`, `is_no_active_device_msg` matches `"404"`, `is_transient_server_err` matches `"500"`… on `format!("{err:#}")`). Scenario: `StartPlayback` on a deleted playlist returns 404 "Not found" → classified as "no active device" → desktop Spotify is launched/nudged, the app waits up to 15 s for the preferred device, transfers, and retries the same failing request. Fix: rspotify's `ClientError::Http(Box<ReqwestError::StatusCode(response)>)` exposes `response.status()`, and the fork's `http_get` already has `status`; classify on the code (and the JSON `error.reason` for `NO_ACTIVE_DEVICE`) via `err.downcast_ref::<rspotify::ClientError>()`, keeping the substring check only as a last resort.
- **S4. `Player` requests block the dispatch loop for every other request** — FORK. [`client/handlers.rs:61-67`](../../spotify_player/src/client/handlers.rs:61). Scenario: even without desktop wake, a `next_track` call stuck in a 429 `Retry-After` sleep stalls `GetCurrentPlayback`, `Search`, `GetContext` and CLI socket replies for up to 30 s. Fix: keep player mutations serialized on a dedicated worker task fed by the dispatcher, so `recv_async` keeps draining.
- **S5. `initialize_playback` aborts on any non-rate-limit error, including "missing image"** — FORK (amplifies UPSTREAM). [`client/mod.rs:280`](../../spotify_player/src/client/mod.rs:280) (`if !is_rate_limit_msg(&err) { return; }`), [`:2405`](../../spotify_player/src/client/mod.rs:2405) and [`:2409`](../../spotify_player/src/client/mod.rs:2409) (`"missing image"` errors). Scenario: current item has no cover (MPRIS fallback without `mpris:artUrl`, an episode without images) → init returns before device selection or desktop wake, with only a log line. Fix: make missing artwork non-fatal; `continue` instead of `return` except on auth errors.
- **S6. Non-hermetic unit test depends on `dbus-send` and a session bus** — FORK. [`desktop_spotify.rs:1307`](../../spotify_player/src/desktop_spotify.rs:1307) `name_has_owner_false_is_not_error`. Scenario: `cargo test` in a container or a runner without a session bus fails with "dbus-send NameHasOwner failed". Fix: skip when `DBUS_SESSION_BUS_ADDRESS` is unset, or `#[ignore]` and run under `dbus-run-session` in CI.
- **S7. `pgrep -x spotify` matches other users' processes** — FORK. [`desktop_spotify.rs:1248`](../../spotify_player/src/desktop_spotify.rs:1248). Scenario: shared workstation, another user runs Spotify → nothing is launched, `wait_for_mpris` spins for `ready_timeout_secs` and fails. Fix: `pgrep -u <uid> -x spotify`.

## 4. Lock order and threading notes (for reviewers of phases 4–6)

Observed order: `ui` → `player` → `data` → `vis_bands`. The UI thread takes `ui` for the whole draw ([`ui/mod.rs:47-77`](../../spotify_player/src/ui/mod.rs:47)) and reads `player`/`data`/`vis_bands` inside; the client handler takes `ui` only to push toasts and never nests ([`state/mod.rs:70-83`](../../spotify_player/src/state/mod.rs:70)); the player-event watcher releases `player` before `ui` and `ui` before `data` ([`client/handlers.rs:177-283`](../../spotify_player/src/client/handlers.rs:177)); `media_control` snapshots under `player` and drops it before D-Bus I/O ([`media_control.rs:37`](../../spotify_player/src/media_control.rs:37)); the streaming thread takes `player.write` then `vis_bands` ([`streaming.rs:273-281`](../../spotify_player/src/streaming.rs:273)); `flume::unbounded` means `send` under a lock never blocks. One inconsistency exists inside the two `ui`-holding threads only: `data → player` ([`ui/page.rs:321`](../../spotify_player/src/ui/page.rs:321) → `:1043`; [`event/window.rs:25`](../../spotify_player/src/event/window.rs:25) → `:332`) versus `player → data` ([`ui/page.rs:426-427`](../../spotify_player/src/ui/page.rs:426); [`event/mod.rs:552-553`](../../spotify_player/src/event/mod.rs:552)). It is harmless today because both threads hold `ui` first (serialized) and no other thread nests `player` with `data`; normalise to snapshot `player` first so a writer-fair `RwLock` cycle cannot appear later. Because `player` is a fair `RwLock`, a pending writer (`retrieve_current_playback`) blocks new readers, so the UI thread holding `ui` while waiting on `player.read()` is the remaining path by which a slow client task stalls keyboard input; phases 4–5 shorten that writer's lead-up by removing the `dbus-send` spawns that precede it. Any new code that needs `ui` and `player` must take `ui` first, and must never hold `ui` across process spawns (S16) or network calls.
